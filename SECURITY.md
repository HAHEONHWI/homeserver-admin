# Security

## Trust boundaries

- Cloudflare Access protects the public hostname; FastAPI verifies every request's signed JWT, issuer, audience, and expiry. Access Passkeys handle login; Access policy and API role allowlists still control authorization.
- The API resolves roles server-side. Passkey login alone does not grant Owner/Operator permissions.
- Dashboard Passkeys are identity-scoped. The API stores only credential public keys and counters; registration requires user verification and a discoverable credential. Challenges expire after 120 seconds and are single-use. Add/remove grants expire after 60 seconds, bind to the subject, operation, and target, and are consumed once.
- API startup clears pending challenges and grants, so restarts and restores invalidate in-flight reauthentication.
- The first dashboard Passkey for an Access subject requires the temporary `WEBAUTHN_BOOTSTRAP_TOKEN`. Issue a new 32-byte token to the intended account, then remove it from the API environment after enrollment. Later Passkey changes require an existing Passkey; the web app keeps tokens only in browser memory, never local storage.
- Live API requests are limited to 120 per minute per verified Access subject and return `429` with `Retry-After` when exceeded. The in-memory limiter is process-local; keep one API replica until it uses shared storage. Development Mock mode skips this limit so UI scenarios can run without throttling; it does not rate-limit login attempts at the Access provider.
- Mutating `/api/v1/` requests are capped at 64 KiB, including chunked bodies, before route handling. The API does not accept file uploads.
- SSE requests authenticate and authorize on every connection, including browser reconnects. Each stream closes within 60 seconds; all streams share a 32-connection limit per API process. Live container logs remain Owner/Operator-only.
- Browser code never receives service tokens or system credentials.
- The Next.js API proxy accepts only the internal `api:8000` service or loopback in local development before forwarding Access assertions.
- Production services run non-root with dropped capabilities. The web/API containers do not mount `/var/run/docker.sock`.
- The host agent runs non-root on an internal-only network. It can read selected `/proc` metric files, `/etc/hostname`, `/etc/os-release`, `/sys/class/hwmon`, and `/sys/devices`, all mounted read-only. It reads only allowlisted hwmon driver names and temperature inputs; `/sys/devices` is mounted so hwmon symlinks resolve, and its other metadata is also accessible if the Agent is compromised. Optional single-file SSD/HDD probes are mounted read-only through `compose.storage.prod.yaml`; the Agent calls `statvfs` without reading probe contents, but the mounted file is accessible to the process, so only non-sensitive files may be selected. Its bearer token is shared only with the API and agent.
- The Portainer read key supports only bounded GET requests for container, image, and endpoint-scoped stack lists, selected-container stats, and logs. A separate `PORTAINER_ACTIONS_API_KEY` enables only fixed container start/stop/restart requests after Owner/Operator authorization and a single-use WebAuthn grant bound to the exact operation and container ID. Portainer tokens inherit user permissions; use a dedicated least-privilege identity limited to the selected endpoint. If the API is compromised, the write key can exercise that identity's Portainer permissions. No Docker socket is mounted.
- The optional GitHub connector uses a fine-grained token with `Actions: read`, an explicit repository allowlist, bounded `GET` requests, and no write operations. The token stays in API environment variables.
- Optional n8n execution history uses the public REST API, sends `X-N8N-API-KEY` only from the API, requests at most five rows, and omits execution data. Use an `execution:list` scope where Enterprise supports scopes; n8n documents that non-Enterprise keys have full account access, so leave this key unset unless that risk is acceptable.
- The Cloudflare read token calls only fixed DNS record `GET` endpoints for one validated Zone ID and stays in API environment variables. Optional writes require a different token scoped to `DNS Write` on that single zone, `CLOUDFLARE_ZONE_NAME`, Owner authorization, same-origin requests, and a one-use WebAuthn grant bound to the full validated A/AAAA/CNAME/TXT/MX change. The API checks the old record before issuing options and rechecks immediately before update/delete, then records before/after values. MX, SPF, DKIM, and DMARC changes show a mail-delivery warning. If the API is compromised, the write token can change records in its configured zone; keep it narrowly scoped and unset it when DNS writes are not needed.
- The optional mailcow connector calls only fixed domain, mailbox, and alias `GET` endpoints with a read-only API key over HTTPS. Mail directory data is restricted to Owner and Operator; no account or alias writes are exposed.
- Optional PostgreSQL metrics use one fixed query inside a `READ ONLY` transaction; the account needs `CONNECT` on its selected database. Remote PostgreSQL connections require `sslmode=verify-full`; the adapter forces this mode and disables GSS encryption so TLS certificate and hostname checks apply. Configure a trusted CA with `sslrootcert=system` or a CA file available inside the API container. Optional Redis metrics use `PING`, the `memory`, `clients`, and `stats` sections of `INFO`, plus `DBSIZE` for the selected database; give the dashboard identity only `+PING +INFO +DBSIZE +SELECT`. `INFO` is categorized as dangerous, so leave it unset unless needed. `redis-py` also needs `SELECT` to select the database in `REDIS_URL`. `rediss://` is required for remote Redis; `redis://` is accepted only for the internal `redis` service hostname or loopback. Both credentials stay in API environment variables, and the database page exposes no SQL console or write operation.
- Optional ntfy delivery uses a server-side token and a validated topic URL. The API sends bounded plain-text alerts only when a host or container warning starts or clears; redirects and proxy environment settings are disabled, and no notification actions are exposed. Anonymous ntfy topics must be treated as bearer secrets.
- The management API is internal-only. Tailscale SSH remains the recovery path.

## Safety rules

- Public signup is disabled. First-Passkey enrollment requires a temporary administrator-issued token and a signed-in Cloudflare Access identity.
- Mock authentication/data are allowed only in development. Production refuses Mock mode.
- Passkey add/remove operations require a target-bound, one-use WebAuthn reauthentication grant and an audit event. Cloudflare DNS writes require the opt-in one-zone token and bind the full change payload to the Owner's one-use grant; revert actions create a new audited DNS write. Web-triggered reboot, shutdown, deployment, rollback, backup, restore, and secret reveal remain disabled until their restricted providers are implemented.
- No arbitrary SQL, shell, privileged Docker run, or unreviewed Compose deployment.
- HomeServer Admin integration secrets are masked and stay server-side. Container output is intentionally shown to Owner/Operator and may contain application secrets; never print credentials to container logs. `.env` files and databases are excluded from Git.
- DNS changes affecting MX/SPF/DKIM/DMARC require a warning and before/after record.

## Operational limits

No live server, Access tenant, provider credentials, or verified disk mount is available in this workspace. Systemd and reboot/shutdown are unavailable; deploy/rollback and SQLite backup/restore exist only as operator-invoked SSH scripts, not web/API controls. Cloudflare DNS changes are not tested against a live zone; the action key is unset, so production DNS stays unchanged. Portainer container actions are implemented behind an optional separate key but are not tested against a live server.
